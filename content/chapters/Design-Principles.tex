\section{The SOLID design principles}
The SOLID principles suggest software architects on how to arrange
functions and data into groupings (e.g., classes), and how these
groupings are arranged.

The goal of the SOLID principles is to create mid-level software structures
(modules) that:

\begin{itemize}
  \setlength{\itemsep}{0pt}
  \item Are easy to understand
  \item Allow changes in the most "comfortable" way
  \item Are the basis of reusable components
\end{itemize}

\section{Open-Closed Principle - OCP}

A software artifact should be \textbf{open for extension but closed for modification}.
Using design patterns to make new funcitonality in a way
that is addictive and not to modify the existing structure.


The behavior of a software artifact ought to be extendible, without having to
modify that artifact.\newline

The aim of OCP is to make the system easy to extend without
requiring too many changes to the system.


\begin{center}
  \begin{minipage}{\linewidth}
    \begin{minipage}{0.6\linewidth}

      Using the open-closed principle, the software architect divides the
      system into components and arranges these components in a
      dependency hierarchy that protects higher-level components from
      changes in lower-level components.


      \paragraph{Example}

      A system displays summary information about a student's career at
      the university on a dashboard: Subjects (those passed with grades), Taxes
      paid and due, Current semester schedule, Next exams, Important notices,
      Stakeholders ask for a printed report with only information on
      subjects and taxes, and a different formatting.\newline

      Generating the report involves two separate responsibilities:\newline
      1. the calculation of the reported data \newline
      2 .the presentation of that data into a web- and printer-friendly form.

\subsection{Liskov substitution principle - LSP}


\begin{center}
  \begin{minipage}{\linewidth}
    \begin{minipage}{0.6\linewidth}
      If for each object o1 of type S there is an object o2 of type T such that
      for all programs P defined in terms of T, the behavior of P is
      unchanged when o1 is substituted for o2 then \textbf{S is a subtype of T}.

If we substrute o2 vitw o1 and the behavior of p
does not change means S is derived class of T.\newline



\begin{center}
  \begin{minipage}{\linewidth}
    \begin{minipage}{0.6\linewidth}
      This principle is about subtyping, not only for inheritance or extension
      but also for the logic, the behavior of the class.

      Derived type must fully support the substitution of their base types:
      functions that use pointers or references to base classes must be able
      to use objects of the derived without knowing it. This is related to the
      substitution property.

      A subtype can replace its supertype only if it behaves the same way.
      This idea, called \textbf{behavioral subtyping}, means the subtype doesn't just
      have the same methods as the supertype — it also follows the same
      rules for how those methods should work. That way, anything the
      client expects from the supertype will also hold true for the subtype.

\subsection{Dependency inversion principle - DIP}

\begin{center}
  \begin{minipage}{\linewidth}
    \begin{minipage}{0.7\linewidth}

      You should always have dependencies that lower modules depend on higher modules,
      not the opposite.
      % Any concrete class only abstract class or interface, not on concrete class.

      \textbf{High-level modules should not depend on anything from low-level
        modules.\newline
        Stable abstractions: abstractions should not depend on details, so
        that changes to details will not affect them.}

      \textbf{Idealistic tension}, in practice each system has at least a concrete
      component: the main function

      We can make an interface:

\paragraph{Example} In Java (or other statically typed languages), this means
that use, import and include statements should refer only to source modules

In dynamically typed languages, source code dependencies should not
refer to modules in which functions being called are implemented.

\subsection{DIP: practical implications}



\begin{center}
  \begin{minipage}{\linewidth}
    \begin{minipage}{0.7\linewidth}
      Dependencies on concretions are tolerable when it comes to
      operating systems, platform facilities and other similar components
      whose changes are tightly controlled and not frequent.

      \textbf{Abstract Factories are helpful} to adhere to the DIP by minimizing the
      number of dependencies on concrete implementations and keep
      them separate from the rest of the system

      In general, volatility should be shifted towards implementation details
      without changing interfaces.
    \end{minipage}% <-- IMPORTANTE: il simbolo % qui evita spazi bianchi extra
    \hfill
    \begin{minipage}{0.3\linewidth}
      \centering
      \includegraphics[width=0.85\linewidth]{images/DesignPrinciples/DP-esempio14.png}
    \end{minipage}
  \end{minipage}
\end{center}

\begin{itemize}
  \setlength{\itemsep}{0pt}
  \item Don't refer to volatile concrete classes
  \item Don't refer from volatile concrete classes
  \item Don't override concreted functions
  \item Never mentions the name of anything concrete and volatile
\end{itemize}

\paragraph{Separation abstract and concrete levels:}  All source code
dependencies point toward the abstract level. The flow of control crosses the
separation line in the opposite direction: this is the sense of "dependency
inversion".

\paragraph{DIP violation}
DIP violations cannot be entirely removed. Some dependencies on concrete
implementations are necessary. They must be minimized and kept separate
